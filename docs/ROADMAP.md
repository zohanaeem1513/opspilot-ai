Development proceeds one phase at a time. Each phase should be independently runnable and testable before the next one starts. Status is updated as work progresses.

| Phase | Description | Status |
|---|---|---|

## Notes

- Phases are intentionally small. A phase should not start until the previous one works end-to-end for its own scope.
- No phase beyond the current one should be scaffolded "early" — this avoids half-finished code sitting unused and keeps the repo honest about what's actually working.
- This table should be updated whenever a phase's status changes.
- **Phase 1 note (resolved in Phase 3A):** `ruff check`/`ruff format --check` could not be run when this phase was originally built — a Windows Application Control policy blocked execution of the downloaded `ruff.exe` on that development machine. As of Phase 3A, both commands run successfully (on a different development machine) and pass with no findings.
- **Phase 2 known limitation:** `npm run lint`, `npm run typecheck`, and `npm run build` all passed, and the page was verified live against a running FastAPI backend (real `service`/`version`/`environment` values rendered) and verified to degrade gracefully (no crash) when the backend was stopped. Responsive Tailwind classes were implemented for mobile widths, but no browser/viewport tool was available in the development environment to visually confirm the mobile layout — that manual check is still pending.
- **Phase 3A scope:** Supabase Postgres schema (`profiles`, `workspaces`, `workspace_members`), SQLAlchemy 2.x async models, Alembic migrations (hand-written initial migration, not autogenerated — no connection was made to a live database during development), and a `GET /ready` connectivity endpoint. See `docs/DATABASE.md` for schema details and `docs/DECISIONS.md` for the Supabase-over-Neon reasoning. `pytest` (mocked database behavior, no real credentials required), `ruff check`, and `ruff format --check` all passed. Migrations have not been applied to any real database — that step is intentionally deferred past this phase.
- **Phase 3B status — done:** `apps/api` — Supabase Auth JWT verification (`app/core/security.py`, dual-path HS256/JWKS, no Supabase SDK or service-role key), auth dependencies (`app/api/deps.py`), app-level profile get-or-create, migration `0002` (`profiles.id → auth.users.id`), and a protected `GET /me` endpoint are implemented. `apps/web` — Supabase session handling (`src/lib/supabase/`), `src/middleware.ts` route guard, `/login`, `/register`, and `/dashboard` pages are implemented — see `docs/DECISIONS.md` for the design. A real Supabase project now exists and is connected (`apps/api/.env`, `apps/web/.env.local`); migrations `0001` and `0002` have been applied to it (`alembic upgrade head`); the register → login → `/dashboard` → `GET /me` flow has been confirmed working end-to-end against real Supabase Auth (ES256/JWKS signing).
- **Phase 3C status — done:** Workspace management. `apps/api` — `POST/GET /workspaces`, `GET/PATCH/DELETE /workspaces/{id}` (`app/api/routes/workspaces.py`), backed by the existing `workspaces`/`workspace_members` tables from migration `0001` — no new migration was needed; the creating user's membership row is written with `role="owner"` instead of the default `"member"`, which is how workspace ownership is represented (see `docs/DATABASE.md`). Authorization (`get_workspace_access` in `app/api/deps.py`) always returns 404, never 403, for both "workspace doesn't exist" and "not a member," so a caller can't distinguish the two by probing UUIDs. `apps/web` — the dashboard now fetches and manages real workspaces (`src/components/workspaces/workspace-manager.tsx`) via Next.js Server Actions (`src/app/dashboard/actions.ts`) that resolve the session server-side, consistent with the rest of the frontend never holding `API_BASE_URL` or an AI/DB credential in browser JS. `pytest` (38/38, including 13 new workspace tests run against an in-memory SQLite database — no real Supabase credentials required), `ruff check`, `ruff format --check`, `npm run lint`, `npm run typecheck`, and `npm run build` all passed.
- **Phase 3C follow-up fix (2026-08-16):** the first real browser test against the actual Supabase database surfaced a bug the SQLite suite couldn't catch: `GET /me` and `GET /workspaces` both 500'd with `sqlalchemy.exc.NoReferencedTableError` for `auth.users`. Root cause and fix are in `docs/DECISIONS.md`; in short, production code never registered a `Table` for Supabase's `auth.users` in `Base.metadata`, only the test file did (for its own SQLite database), so real Postgres queries failed a resolution step the tests never exercised for real. Fixed by adding `apps/api/app/db/models/supabase_auth.py` and a matching Alembic `include_object` exclusion; verified with read-only queries run directly against the real Supabase database (see `docs/DECISIONS.md`) and two new regression tests (`apps/api/tests/test_db_models.py`, 40/40 passing). Full authenticated browser click-through is still the user's to confirm.
- **Phase 4 status — done (verified 2026-10-05):** document upload/list/get/delete is implemented and verified against the real connected Supabase Storage bucket and browser flow. `apps/api`: `documents` table (migration `0003`), `POST/GET /workspaces/{id}/documents`, `GET/DELETE /workspaces/{id}/documents/{document_id}` (`app/api/routes/documents.py`), authorized via the existing `get_workspace_access` dependency; file bytes go to a private Supabase Storage bucket via the `DocumentStorage` abstraction (`app/core/storage.py`) called directly over its REST API (`httpx`, no Storage SDK), not Postgres. `apps/web`: upload form + document list embedded per-workspace in the dashboard (`src/components/workspaces/document-manager.tsx`), via Server Actions and `src/lib/api.ts` functions. The previously pending real-environment gap is now closed: the bucket exists, uploads work through the browser, files are stored successfully, and document metadata is visible in the dashboard.
- **Phase 5 status — done (2026-10-05):** document processing now runs after upload. `DocumentStorage` now supports `download()` so uploaded files can be read back from Supabase Storage. `app/services/text_extraction.py` extracts UTF-8 text from `.txt` files and selectable text from PDFs using `pypdf`; `app/services/chunking.py` normalizes and splits text into overlapping chunks; `app/services/embeddings.py` generates normalized local embeddings with Sentence Transformers using `all-MiniLM-L6-v2`; and `app/services/document_processing.py` coordinates download → extraction → chunking → embedding → persistence. Migration `0004_document_processing.py` enables pgvector support for this flow, adds `documents.status` and `documents.processing_error`, and creates `document_chunks` with `vector(384)` embeddings plus document/workspace indexes and a unique `(document_id, chunk_index)` constraint. The frontend now displays processing status and errors. Real TXT and text-based PDF uploads were verified as `Processed`; a whitespace-only TXT file was verified as `Failed` with `document contains no extractable text`; and a direct database query confirmed a stored chunk with `vector_dims(embedding) = 384`. `pytest` passes 52/52, `ruff check` passes, `npm run lint` passes, and `npm run build` passes. The only current frontend build note is the non-blocking Next.js warning that the `middleware` file convention is deprecated in favor of `proxy`
